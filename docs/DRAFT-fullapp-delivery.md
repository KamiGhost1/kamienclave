# DRAFT — Режим доставки полного приложения (Full-App Delivery)

Статус: черновик для обсуждения · Дата: 2026-06-01 · Версия: 0.1
Дополняет [TECHNICAL.md](../TECHNICAL.md); ничего из существующего не заменяет.

---

## 0. TL;DR

Добавить kamienclave **второй режим работы** наряду с bytecode mini-VM:

- **Режим A (есть):** `bytecode` — сервер компилирует JS-подмножество в закрытый
  watermarked bytecode, клиент исполняет в mini-VM в памяти. Сильная
  непрозрачность, но узкий язык (не Node).
- **Режим B (этот драфт):** `fullapp` — сервер отдаёт **целое настоящее
  приложение** (например, NestJS-бэкенд) подписанным и зашифрованным; клиентский
  загрузчик расшифровывает его в памяти и запускает на штатном Node.js. Полная
  совместимость с реальным стеком, но **защищает доставку и контроль, а не
  секретность кода от root** (см. §2).

Оба режима делят один транспорт, лицензирование, выдачу/отзыв и watermarking —
то, что уже построено. Новое в режиме B — формат пакета приложения, загрузчик и
честно очерченная (более слабая) модель угроз.

---

## 1. Зачем это и что мы переиспользуем

Запрос: «отдавать подписанный и зашифрованный полный файл Nest-бэкенда, и чтобы
он работал». Mini-VM этого не может (не Node, узкое подмножество — см.
TECHNICAL §7.1). Но **весь остальной аппарат уже подходит как есть**:

| Существующий компонент | Роль в режиме B |
| ---------------------- | --------------- |
| `internal/server` (store, api, licensing) | выдача/отзыв/учёт лицензий, endpoint доставки |
| Протокол `/v1/fetch` (Ed25519 + X25519 + AEAD + JCS + SPKI-pin) | защищённая доставка пакета; **payload-байты могут быть чем угодно** |
| `license.Bundle` (Argon2id sealed) | несёт ключ расшифровки приложения вместо/вместе с bytecode-секретами |
| `serverkit/watermark` (идея §8.4.1) | per-license отпечаток внутри бандла приложения для атрибуции утечки |
| hardening (integrity-stamp, anti-debug, signal-zeroize) | защита самого загрузчика |
| kill-switch / ротация / телеметрия | работают одинаково в обоих режимах |

Транспорт уже payload-agnostic: сервер шифрует произвольные `[]byte` сессионным
ключом и подписывает ответ. Поэтому «доставка целого приложения» — это в основном
**новый формат пакета + загрузчик**, а не новый протокол.

## 2. Модель угроз — читать до проектирования

> **Жёсткая правда (тот же §1.1).** Node.js должен видеть исполнимый JS/байткод,
> чтобы его выполнить. Значит атакующий с root на машине клиента в итоге снимет
> распакованное приложение из памяти процесса Node. Режим B **не делает код Nest
> секретным от такого атакующего.**

Что режим B **реально даёт** (и это немало):

1. **Защита в покое и в доставке.** На диске клиента — только зашифрованный
   подписанный бандл; открытого исходника нет. Без валидной лицензии (и ключа из
   неё) бандл — это шум.
2. **Контроль и enforcement.** Лицензия гейтит запуск; `revoke` = kill-switch;
   ротация — отдать новый бандл; expiry — встроена. Перепродажа/casual-копирование
   отсекаются.
3. **Атрибуция.** Per-license watermark внутри бандла → утёкшую копию привязываем
   к лицензии (детерренс + юридический рычаг).
4. **Целостность и подлинность.** Бандл подписан сервером; клиент не запустит
   подменённый код.

Что режим B **не даёт** (фиксируем честно):

- Секретность кода от root/решительного RE — расшифрованный JS живёт в памяти V8;
  `--inspect`, дамп heap, патч Node-бинаря его достают.
- Это **слабее**, чем mini-VM (режим A): там в памяти нечитаемый bytecode под
  неизвестную VM; здесь — обычный исполнимый JS. Разный класс защиты — это нужно
  явно сказать пользователю при выборе режима.

**Вывод по позиционированию:** режим B — про **«зашифрованная лицензируемая
дистрибуция настоящего приложения»**, а не про «неизвлекаемый код». Для усиления
комбинируется с обфускацией (§5) и гибридом (§7).

## 3. Формат пакета приложения (`.encpkg`)

Самодостаточный, потоково-расшифровываемый, версионированный.

```
encpkg := header || enc(manifest) || enc(payload-tar)
header  := magic("ENCPKG1") | version(u16) | flags(u16)
         | nonce(12) | manifest_len(u32) | payload_len(u64)
manifest (JSON, зашифрован):
  {
    "app_id":        "acme-nest-backend",
    "version":       "1.4.2",
    "entrypoint":    "dist/main.js",         // что запускать под Node
    "node_semver":   ">=20 <23",             // требуемый рантайм
    "args":          ["--max-old-space-size=512"],
    "env_passthrough":["PORT","DATABASE_URL"],// какие env пробросить
    "watermark":     "<per-license fingerprint>",
    "files_sha256":  "<хеш payload-tar до шифрования>"
  }
payload:
  единый ncc-бандл — один `index.js` (pure-JS, см. §9 Q1).
  Опционально sidecar-ассеты (не-native: .json/.wasm/шаблоны), если есть.
```

- Вход — **уже собранный `@vercel/ncc` single-file** (`index.js`); поставщик
  отвечает за сборку. Мы принимаем один JS-файл (+ опц. sidecar-ассеты).
- Шифрование: AES-256-GCM (тот же `crypto/aead`), ключ — из лицензии (§4).
- Подпись: Ed25519 сервера поверх всего `.encpkg` (тот же `crypto/sign`).
- `files_sha256` в манифесте — integrity бандла после расшифровки.
- Watermark вшивается сервером в бандл до шифрования (см. §6).
- `entrypoint` фиксируется в `index.js`; для single-file `payload` можно
  хранить не tar'ом, а прямым blob'ом + (если нужны) короткий список sidecar.

## 4. Ключи и лицензия

Переиспользуем `license.Bundle`, добавив поле для режима B:

- `AppDecryptKey []byte` (32) — ключ AES для `.encpkg` этой лицензии (аналог
  `BCConstKey` в режиме A). Едет в sealed bundle, на сервере хранится в записи
  лицензии.
- `Mode string` — `"bytecode" | "fullapp"`, чтобы клиент знал, как трактовать
  ответ `/v1/fetch`.

Поток ключей:
1. `license issue --mode fullapp` → сервер генерирует `AppDecryptKey`, кладёт в
   запись и в sealed bundle клиента.
2. Сервер шифрует `.encpkg` этим ключом (per-license → у каждого клиента свой
   шифротекст, что также делает watermark неизбежным).
3. Клиент при `run` достаёт `AppDecryptKey` из распакованного bundle и
   расшифровывает полученный `.encpkg` в памяти.

> Доставка `.encpkg` может идти двумя путями: (а) целиком в теле ответа
> `/v1/fetch` (как сейчас bytecode), либо (б) ответ возвращает короткий
> pre-signed URL + ключ, а сам бандл качается отдельным GET (для больших Node-
> бандлов это разумнее — десятки МБ). Решить на этапе проектирования (§9, Q4).

## 5. Клиентский загрузчик (`enclave-host`)

Новый бинарь/режим: распаковывает и запускает приложение.

```
enclave-host run --license-file acme.lic [--ca ...]
  1. hardening.Init()  (как в enclave-vm: anti-debug, integrity, signal-zeroize)
  2. unlock bundle (passphrase) -> ключи + Mode=fullapp
  3. fetch .encpkg по протоколу /v1/fetch
  4. verify подпись Ed25519, decrypt AES-GCM ключом из bundle
  5. verify manifest.files_sha256
  6. материализовать payload-tar:
       — Вариант 1 (tmpfs/ramdisk): распаковать в memory-backed FS, запустить
         `node entrypoint`, по выходу — затереть и размонтировать.
       — Вариант 2 (fd/pipe): отдать single-file bundle Node через stdin/--eval
         или /dev/fd, не касаясь диска вообще.
  7. проброс env из manifest.env_passthrough; запуск дочернего Node.
  8. teardown: zeroize ключей и буферов, удаление временных артефактов.
```

**Раз вход — pure-JS ncc single-file, путь конкретизируется** (как не писать
расшифрованный код на постоянный диск):

- **[РЕАЛИЗОВАНО, проверено на живом Nest-бэкенде] no-disk через tmpfs:**
  расшифрованный бандл пишется во временный файл на **tmpfs (RAM, `/dev/shm`)**,
  `0600`, запускается `node <path>`, и **анлинкается через ~1.5с после старта**
  (Node уже открыл файл и держит fd → путь исчезает из директории, процесс
  работает из открытого in-RAM fd), гарантированно удаляется на выходе.
  **Главная находка B0 (стоила трёх итераций на реальном артефакте):** memfd и
  stdin **НЕ годятся** для настоящих ncc/webpack/NestJS-бандлов:
  - `node /dev/fd/N` → `realpath()` на entry → `/memfd:... (deleted)` → ENOENT;
  - `node -` (stdin) → webpack-бандл молча не бутстрапится (завязан на
    `require.main`/`__filename`), процесс крутит CPU без вывода;
  - `node <tmpfs-path>` → бутстрапится штатно. Подтверждено: NestJS поднялся,
    `curl /auth/health` → `{"status":1}`, `POST /auth/login` → 200; файл анлинкнут,
    `/dev/shm` чист. **Честная оговорка (§2):** это слабее true-memfd — бандл
    кратко (окно старта) виден как `0600`-файл в RAM; но режим B и так уступает
    root, а root читает память процесса в любом случае.
- **Альтернатива — `node --eval "<code>"`:** код передаётся аргументом/через
  stdin. Проще, но виден в `/proc/<pid>/cmdline` (для stdin-варианта — нет);
  длинные бандлы лучше через fd/stdin, не argv.
- **tmpfs / ramdisk** (fallback): распаковка в RAM-FS, удаление при выходе. Файлы
  кратко видны процессам с правами — слабее, но переносимее.
- **`node:sea`/эмбеддинг** — не нужно при ncc-входе; оставляем как опцию только
  если позже понадобится пиннить версию Node (§9 Q3).

Sidecar-ассеты (если есть, не-native) — кладутся в tmpfs рядом и удаляются на
teardown. Native-аддоны исключены входным контрактом (§9 Q2).

## 6. Watermarking полного приложения

Перенос идеи §8.4.1 на JS-бандл (вместо bytecode-констант):

- Сервер при сборке `.encpkg` для лицензии вшивает отпечаток в **избыточных,
  семантически-инертных** местах: строковые константы, порядок необязательных
  полей, «мёртвые» ветки, комментарии в map-файлах. Размазать ≥N копий с CRC,
  как в `watermark.Embed`.
- Извлечение из утёкшей копии — majority-vote по уцелевшим копиям → license id.
- Опционально: **динамический** watermark — приложение в рантайме шлёт на сервер
  свой fingerprint (телеметрия), что даёт ещё и факт «где и когда запускалось».

Это cost-raising + атрибуция, не предотвращение (та же оговорка §2).

## 7. Усиление и гибрид (рекомендации)

Режим B сам по себе — «обычный JS в памяти». Усилить, не меняя сути:

1. **Обфускация до упаковки:** `javascript-obfuscator` (агрессивные пресеты) +
   `bytenode` (V8-байткод `.jsc`) на исходнике Nest *перед* `.encpkg`. Поднимает
   стоимость снятия из памяти. (bytenode разбираем публично — это speed bump.)
2. **Гибрид с режимом A:** тело Nest едет режимом B (полная совместимость), а
   2–3 действительно секретных алгоритма вынесены в bytecode-payload (режим A) и
   вызываются изнутри Nest через host-bridge/IPC. Тогда самое ценное получает
   сильную защиту mini-VM, а остальное — лицензируемую дистрибуцию.
3. **Тонкий клиент для ядра:** если что-то не должно покидать твою инфру вообще —
   оставить это серверным вызовом (см. TECHNICAL §1.1, «единственная настоящая
   защита»).

## 7a. Гибрид B+A: env-конфиг в контейнере + секреты в mini-VM

Целевая архитектура для типичного NestJS-бэкенда (уточняет §7.2):

- **env приходит в контейнер** (k8s/compose secrets, не файл) → `process.env`
  чистый, no-disk через `/dev/fd` без `__dirname`-проблем.
- **в env — только НЕ-секретное** (адреса БД/Redis, порты, флаги). Это данные
  клиента, он их видит — нормально.
- **настоящие секреты** (ключи к ВНЕШНИМ API, проприетарные константы/формулы,
  криптоподпись с секретным ключом) — **не в env**, а в bytecode-payload режима
  A, исполняемом в mini-VM анклава. NB: если таких секретов нет (см. ниже —
  частый случай), режим A не нужен, и кейс сводится к чистому режиму B.

### Критическое правило: VM отдаёт РЕЗУЛЬТАТ операции, а не сам секрет

Развилка, определяющая, реальна защита или иллюзорна:

- ❌ **VM возвращает секрет как значение** (`jwtSecret = enclave.get(...)` →
  строка в памяти Nest). **Иллюзия.** Как только секрет материализовался строкой
  в heap V8, атакующий с root снимает его дампом — ровно как из env. Mini-VM
  потрачена впустую, выигрыша против модели угроз (root у клиента) ноль.
- ✅ **VM выполняет операцию, секрет не покидает анклав**
  (`token = enclave.signJWT(payload)` — ключ живёт и используется ВНУТРИ
  bytecode-VM, наружу выходит только результат). Достать ключ = реверсить
  bytecode-VM (нечитаемый, watermarked, per-license), а не дампить heap. Это и
  есть смысл режима A.

> **Правило:** анклав отдаёт результаты операций над секретом, а не секрет.
> «Подпиши это / расшифруй то / посчитай по формуле» — да. «Дай ключ» — нет.

Следствия:
- Секрет (напр. JWT-ключ) должен попадать в VM **не через env** — он
  вкомпилирован в bytecode-payload (per-license, шифрованный, watermarked) или
  доставляется тем же `/v1/fetch`. Т.е. ключ — часть payload режима A, не конфиг.
- mini-VM из «калькулятора» становится **сервисом операций для приложения** →
  понадобятся host-функции, которых пока нет (намеренно не добавляли
  спекулятивно — добавляются только под реальную потребность конкретного
  секретного ядра, напр. `crypto.sign`/`crypto.verify`/`crypto.sha256`).
- Нужен канал **Nest → анклав**: Nest запускает `enclave-vm` подпроцессом/через
  сокет, шлёт вход, получает результат (IPC).

### Что НЕ является кандидатом в режим A (важно)

Не всё «про безопасность» — секрет, достойный mini-VM. Критерий: в анклав идёт
**долгоживущий секрет, над которым выполняется операция**, а не любая
auth-логика.

- **Авторизация через lookup в хранилище клиента (напр. токен → Redis/БД) — НЕ
  кандидат.** Если метод смотрит токен в хранилище клиента, не проверяет
  криптоподпись и не держит секретного ключа — логика тривиальна и опирается на
  данные клиента в его же инфре. Реверсить нечего, прятать нечего; коннект к
  хранилищу и так в env. → такую авторизацию в анклав НЕ выносим.
- Следствие: если auth был единственным кандидатом, **гибрид §7a не нужен** —
  кейс сводится к чистому режиму B (зашифрованная лицензируемая дистрибуция
  всего Nest). mini-VM остаётся отдельным режимом продукта для случаев, где
  есть настоящий вычислительный IP (см. ниже).

**Реальные кандидаты в режим A** (если присутствуют в бэкенде): проприетарные
алгоритмы (биллинг/тарификация, scoring, матчинг, ранжирование, ценообразование,
антифрод-правила), бизнес-формулы/коэффициенты, **ключи к ВНЕШНИМ сервисам**
(не к БД клиента — к твоим API/платёжкам), которые не должны попасть клиенту.
Нет такого → режим A избыточен, и это нормально.

### Честная граница гибрида (назвать вслух)

- Защищается **долгоживущий секрет** (ключ подписи), а не эфемерный результат.
  Подписанный JWT в момент использования живёт в памяти Nest открыто — это
  нормально, токен и так уходит наружу. Украсть один токен ≠ украсть ключ.
- Пока процесс жив, атакующий видит факт вызова и может использовать анклав как
  **оракул** («подпиши мне это»). Защита — лицензия/kill-switch + то, что оракул
  работает лишь у легитимно запущенного экземпляра. Для anti-piracy приемлемо.

## 8. Что добавить в код (ориентир по объёму)

| Кусок | Где | Примечание |
| ----- | --- | ---------- |
| `Mode` + `AppDecryptKey` в bundle/store | `internal/license`, `internal/server/store` | малый |
| Формат `.encpkg` (encode/decode, подпись, AEAD) | новый `internal/encpkg` | средний |
| Серверная сборка `.encpkg` (bundle→watermark→encrypt→sign) | `internal/serverkit` (рядом с factory) | средний |
| `license issue --mode fullapp` | `cmd/enclave-server` | малый |
| Доставка: тело `/v1/fetch` или pre-signed URL | `internal/server/api` | средний (зависит от §9 Q4) |
| Загрузчик `enclave-host` (unlock→fetch→decrypt→run Node) | новый `cmd/enclave-host` | **крупный**, основной риск |
| In-memory материализация (tmpfs / fd / `--eval`) | `enclave-host` | **крупный**, требует прототипа на реальном приложении |
| Watermark JS-бандла | `serverkit/watermark` (расширить) | средний |
| e2e: issue fullapp → fetch → run целевого приложения | тесты | средний |
| **[только если есть секретное ядро] гибрид §7a:** `crypto.*` host-функции, приложение→анклав IPC, секрет-в-payload, e2e | `runtime/host`, новый IPC-режим, `serverkit/factory` | крупный, **по потребности** |

Доминирующая неопределённость и риск — **загрузчик + способ запустить Node без
утечки на диск против настоящего NestJS-бандла** (native-аддоны, размер, single-
file сборка). Это надо прототипировать первым, на реальном артефакте.

## 9. Открытые вопросы (решить до старта)

1. **[РЕШЕНО]** Сборка приложения: на вход подаётся **уже собранный через
   `@vercel/ncc` единый бандл** (`index.js`). Поставщик отвечает за сборку; мы
   принимаем один JS-файл. Это резко упрощает in-memory запуск (см. §5) и
   позволяет no-disk через `node --eval`/fd. Следствие для §3: payload-tar
   вырождается в один файл (+ опц. sidecar-ассеты, см. Q2).
2. **Native-аддоны** (`*.node`, напр. bcrypt, sharp, pg-native): **ncc их НЕ
   инлайнит** — он выкладывает `.node` рядом с бандлом отдельными файлами. То
   есть «единый бандл» перестаёт быть единым, если в зависимостях есть native.
   Решить: (а) запретить native (чистый JS only — тогда truly single-file и
   no-disk работают), либо (б) поддержать sidecar `.node`-файлы — но они
   обязаны лечь на реальный диск (Node грузит аддоны через `dlopen`, из памяти
   нельзя) → для них защита «в покое» теряется, нужен whitelist/предустановка.
   **Рекомендация B0:** начать с (а) pure-JS ncc-бандла; native — отдельный
   этап с явно ослабленной гарантией.
3. **Node runtime:** клиент использует свой Node (проверять `node_semver`) или мы
   поставляем пиннутый Node (`node:sea` / встроенный) ради воспроизводимости и
   контроля версии?
4. **[РЕШЕНО]** Доставка больших бандлов: реализована **out-of-band доставка**.
   `/v1/fetch` возвращает (внутри зашифрованного CT) `BlobDescriptor` с
   одноразовым TTL-токеном; клиент отдельным GET `/v1/blob?token=` качает blob.
   Сам blob — самозащищённый `.encpkg` (AEAD на app-ключе + подпись), токен лишь
   авторизует скачивание. `transport.Fetch` делает это прозрачно (см. поле
   `FetchResponse.Delivery`). Bytecode остаётся inline.
5. **Уровень in-memory гарантии:** tmpfs (файлы кратко видны) приемлем, или нужен
   строгий no-disk (fd/`--eval`, что ограничивает форму приложения)?
6. **Платформы:** только Linux (tmpfs/`/dev/fd` доступны) или ещё Windows/macOS
   (там in-memory сложнее)?
7. **Совместимость с hardening:** дочерний Node — отдельный процесс; наши
   anti-debug/integrity защищают загрузчик, но не сам Node. Нужна ли защита
   дочернего процесса (ptrace-scope, no-dump для child) и в каком объёме?

## 9a. Совместимость целевого приложения и конфигурация

> Защищаемое приложение — внешний по отношению к этому проекту артефакт. Здесь —
> только общие правила совместимости; конкретные приложения не документируются и
> не коммитятся. Если целевому приложению потребуется адаптация под защиту, она
> делается на стороне того приложения.

**Типичный NestJS-стек ncc-дружелюбен** — большинство пакетов pure-JS
(`@nestjs/*`, `ioredis`, `pg` без `pg-native`, `mongodb` с pure-JS bson, `knex`,
`passport-*`, `rxjs`, валидаторы) бандлятся в единый `index.js`.

**Главный риск совместимости — native-аддоны** (`.node`): ncc их не инлайнит, из
памяти они не грузятся (`dlopen` нужен файл). Типичные виновники и обход:
- `bcrypt` → `bcryptjs` (pure-JS, drop-in, тот же API);
- `pg-native` → штатный `pg` (pure-JS);
- `better-sqlite3`/`sharp`/`kerberos` и пр. → если в рантайме, ломают
  truly-single-file: либо избегать, либо sidecar `.node` на диск (тогда no-disk
  теряется только для аддона, см. §9 Q2).
- **Чек на B0:** убедиться, что рантайм-бандл pure-JS (нет `.node` рядом).

**ncc-warnings** про лениво-загружаемые опциональные пакеты
(`@nestjs/microservices`, `@nestjs/websockets`, `class-transformer/storage`) —
не ошибки; бандл рабочий, если они не используются.

### Конфигурация через env — работает, но с явной границей

Дочерний Node — обычный процесс; `@nestjs/config`/`process.env` работают штатно.

> **Принцип: env/конфиг — это данные КЛИЕНТА, не твой секрет. Защищается код,
> а не конфигурация.** `DATABASE_URL`, пароли к БД, JWT-секрет задаёт и видит
> клиент на своей машине — это нормально (он подключает сервис к своей инфре).

Подача конфига:
1. **`process.env`** (предпочтительно) — загрузчик пробрасывает дочернему
   процессу переменные (`manifest.env_passthrough` или наследование окружения).
2. **`.env`-файл** — лежит на диске клиента как обычно (не входит в зашифрованный
   бандл), читается через `ConfigModule.forRoot({ envFilePath })`.

Осторожно:
- **Секрет, который надо скрыть ОТ клиента, в env класть нельзя** — клиент
  прочитает `process.env`. Такое (напр. твой ключ к внешнему API) — только через
  серверный прокси или в зашифрованном коде, не в конфиге.
- **`__dirname`/`cwd`-относительные чтения** при no-disk (`/dev/fd/N`) ломаются:
  у бандла нет «своей папки». Касается `.env` рядом с бандлом, swagger-статики,
  шаблонов. Решения: env через `process.env` (способ 1), абсолютные пути, либо
  материализовать рабочую директорию/ассеты в tmpfs.
  - **Авто-миграции в bootstrap** (если приложение гоняет миграции из кода по
    пути к папке при старте) — типичный нарушитель no-disk. Если миграции
    прогоняются отдельным шагом вне бандла — проблемы нет. Проверить на B0 для
    конкретного приложения.

## 11. Связь с существующим дизайном

- Не ломает режим A: `Mode` разводит пути на клиенте и сервере.
- Переисповать: транспорт (§5 TECHNICAL), лицензирование (§14), watermark (§8.4.1),
  hardening (§8), sealed bundle (§6.1).
- Новое и только здесь: формат `.encpkg`, загрузчик Node, in-memory запуск,
  watermark JS-бандла, более слабая (явно задокументированная) модель угроз §2.
- Позиционирование для пользователя: **режим A — «неизвлекаемая логика, узкий
  язык»; режим B — «настоящее приложение, лицензируемая зашифрованная
  дистрибуция»**. Выбор — осознанный компромисс полнота↔непрозрачность.
